# `apps/vinext`

The RealWorld commerce demo on [vinext](https://github.com/cloudflare/vinext) 1.3.1 (the Next.js API surface on Vite), deployed to Cloudflare Workers with the Cloudflare Vite plugin (v2 beta) and the `cf` CLI.

**Live:** https://realworld-vinext.wataru-chame-gon.workers.dev

Pages mirror [next16-commerce](https://github.com/aurorascharff/next16-commerce): home (featured products, categories, recommendations), catalog with search, category filter, sort and pagination (`/all`), product detail with rating, stock and reviews (`/product/[id]`), cart (`/cart`), saved products (`/saved`), account profile (`/account`), sign-in (`/sign-in`) and about (`/about`). All data and Server Functions come from `@realworld/core`; components come from `@realworld/ui`. App code is limited to routes, thin feature components in `features/`, and `lib/`.

## Commands

```bash
pnpm dev               # cf dev   (Vite dev server, workerd, local D1 + KV)
pnpm build             # cf build (vite build → .cloudflare/output)
pnpm preview           # vite preview: the production build in workerd, local bindings
pnpm deploy            # cf deploy
pnpm db:setup:local    # migrate + seed the local D1 that the Vite plugin uses
pnpm db:setup:remote   # migrate + seed the remote D1 (realworld-vinext)
pnpm test              # Vitest (app helpers)
pnpm test:e2e          # Playwright against the production build (vite preview)
PLAYWRIGHT_BASE_URL=https://realworld-vinext.wataru-chame-gon.workers.dev pnpm test:e2e
```

`cf dev` cannot forward flags (such as `--port`) to Vite; run `vite dev` directly when you need them.

Both were created with `cf d1 create` and `cf kv namespaces create`, and are declared in `cloudflare.config.ts`. The remote database was migrated and seeded through the `@realworld/db` package scripts (`pnpm db:setup:remote`). Wrangler was not used.

## Wiring

- **D1**: `lib/database.ts` calls `configureDatabase(() => env.DB)` with `env` from `cloudflare:workers`; the root layout imports it.
- **Data cache**: `vite.config.ts` registers `kvDataAdapter()` from `@vinext/cloudflare` as vinext's data cache, so `'use cache'` entries, `cacheTag` metadata and `updateTag` markers live in Workers KV and survive across isolates and deployments.
- **Render stages**: the `vinext` export condition selects `@realworld/core/render-stages`' no-op fallback. Vite's top-level `resolve.conditions` only reaches the client environment, so `vite.config.ts` also sets it for the `rsc` and `ssr` environments. With the top-level setting alone, the build fails with `"prefetch" / "navigation": Missing export` from vinext's `next/cache` shim.
- **Workspace packages**: vinext's `"use cache"` and `"use server"` transforms inject imports of `@vitejs/plugin-rsc` into `packages/core` source. pnpm's strict layout can't resolve them from there (`Rolldown failed to resolve import "@vitejs/plugin-rsc/react/rsc/server"`), so `resolve.dedupe` resolves them from the app.
- **Local state**: the Cloudflare Vite plugin persists local D1/KV in `apps/vinext/.cloudflare/state`, not in `cf`'s default `~/.config/cloudflare/state`. That is why `db:setup:local` passes `--persist-to`.

## What vinext could not do (as of 2026-10-28)

Tested with vinext 1.3.1, `@vinext/cloudflare` 1.2.1, `@cloudflare/vite-plugin` 2.0.0-beta.v.5 and React 19.3.1 on Cloudflare Workers. Each of these works in Next.js 16.5 canary and is used by this app; the second column is what the app does instead.

| Feature (what it does in Next.js)                                                                                                                              | On vinext, and what this app does instead                                                                                                                                                                                            |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Static shell / Partial Prerendering** (`cacheComponents`): the layout and cached parts of a page are served static and only dynamic holes render per request | No static shell. Every page that reads a cookie anywhere (here the header's cart badge and account menu) renders entirely per request (`cache-control: private, no-store`). Cached reads still come from KV, so the render is cheap. |
| **Partial Prefetching** (`partialPrefetching`): a `<Link prefetch>` carries the route's cached content, so the navigation shows it instantly                   | Option ignored. Links prefetch only a loading shell (layouts + Suspense skeletons); the cached product data arrives with the navigation (~250 ms in production).                                                                     |
| **`prefetch()` / `navigation()` render-stage gates** (`next/cache`): choose whether content goes into a link prefetch or waits for the navigation              | Not exported (`Missing export` at build). `@realworld/core`'s `vinext` export condition makes them no-ops, so the gated content renders with every request.                                                                          |
| **`ensureStatic`** segment config: build-time assertion that a route or layout stays static up to a given stage                                                | Silently ignored, with no error or warning. The exports stay for parity with the Next.js app.                                                                                                                                        |
| **`instant`** segment config: validates that navigations into a segment render instantly                                                                       | Silently ignored.                                                                                                                                                                                                                    |
| **`instant()` from `@next/playwright`**: holds dynamic content back so a test can assert what the prefetched UI shows                                          | No instant-navigation lock. The e2e suite asserts that dynamic content does appear inside the scope, documenting the difference.                                                                                                     |
| **`'use cache: private'` in the browser**: per-session results cached client-side so per-user content can be prefetched                                        | Per request only; never kept in the browser or KV. Functionally correct.                                                                                                                                                             |
| **`<ViewTransition>` around streamed content** (the shared `AnimatedSuspense`): skeleton exits and content enters with an animation                            | SSR fails with `Element type is invalid … got: undefined`. The product page uses plain `<Suspense>`; shared-element transitions (`<ViewTransition name share>`) and navigation view transitions do work.                             |
| **`router.push()` right after an `updateTag` Server Function**: navigates with fresh data                                                                      | Pushing the current URL replays the stale client route cache (a signed-out user still saw their name). The app relies on the Server Function's own re-render instead.                                                                |
| **Build-time prerendering with `generateStaticParams`**                                                                                                        | Not prerendered (no `prerender` option configured, and D1 is not reachable at build time); routes render on demand.                                                                                                                  |

## Cache Components on vinext: what works

Verified on the deployment above (version `d681b5c3`) on 2026-10-28, plus the local production build. ✅ works, ⚠️ partial or different semantics, ❌ not supported (closest equivalent in use).

| Feature                                          | Status | What happens on vinext 1.3.1 (evidence)                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cacheComponents: true`                          | ⚠️     | Read from `next.config.ts`. It turns on vinext's "PPR runtime" (fallback/loading shells used for link prefetches), but pages are not split into a static shell plus dynamic holes. Every HTML response here is rendered per request: `cache-control: private, no-cache, no-store, max-age=0, must-revalidate` on `/`, `/about`, `/all`, `/product/17` and `/cart`. The header reads the session cookie on every page.                                                                                   |
| `'use cache'`                                    | ✅     | Stored in KV through `kvDataAdapter`. After the e2e run there were 82 entries under `realworld-vinext:cache:use-cache:build:…`, each tagged in KV metadata (`categories`, `products,product:17`, `reviews:17`, `cart:<id>`, `saved:<id>`, `account:<id>`).                                                                                                                                                                                                                                              |
| `'use cache: remote'`                            | ✅     | Treated as the shared `'use cache'` (same KV store): `stock:<id>`, `featured-products`, and catalog-page entries. A never-seen search `/all?q=…`: first request 0.80–0.96 s, then 0.16–0.41 s.                                                                                                                                                                                                                                                                                                          |
| `'use cache: private'`                           | ⚠️     | Works per request only. vinext's runtime documents it as "per-request cache (not shared across requests)", and no `session` entry exists in KV. Next.js keeps it in the browser so per-session reads can be prefetched; vinext re-reads the cookie on every request. Sign-in/out and per-user reads behave correctly (e2e).                                                                                                                                                                             |
| `cacheLife`                                      | ✅     | Each entry stores `revalidateAt` / `expireAt` and is served stale-while-revalidate by profile. The KV TTL is `max(30 days, expire)`: `cacheLife('max')` entries (cart, saved, account, featured) expire in 365 days; `minutes`/`hours`/`days` entries keep the adapter's 30-day TTL and go stale by their stored profile.                                                                                                                                                                               |
| `cacheTag`                                       | ✅     | Tags are written to each KV entry's metadata (see above).                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `updateTag` in Server Functions                  | ✅     | Writes tag markers (`realworld-vinext:__tag:session`, hashed `__tag:__hash:…` for `cart:<id>`, `saved:<id>`, `account:<id>`), and the Server Function response re-renders the current route. In production e2e, the cart badge, cart lines, saved list, profile and signed-out header all update without a reload. Caveat: `router.push()` to the current URL after the Server Function replays the stale client route cache (the header kept the signed-out user's name), so the app does not do that. |
| Partial Prefetching (`partialPrefetching: true`) | ❌     | The option is not read anywhere in vinext (no warning). Closest equivalent: `<Link prefetch>` fetches a `prefetch-loading-shell` RSC payload (6.3 KB for `/product/17`, page-cached with `x-vinext-cache: HIT`, `s-maxage=31536000`): layouts and Suspense skeletons only, without the cached product name, details, stock or reviews. The cached data comes with the navigation; in production the product header was visible 254 ms after the click.                                                  |
| `<Link prefetch={true}>`                         | ✅     | Prefetched in production builds when visible: 14 prefetch requests on `/` (modes `prefetch-loading-shell`, `prefetch-dynamic-shell` for `/all`). Links without `prefetch` are fetched without a shell mode.                                                                                                                                                                                                                                                                                             |
| `ensureStatic`                                   | ❌     | Silently ignored: no build error or warning, and no reference in vinext's source. `/about` (`ensureStatic = 'navigation'`) is served `private, no-store` like every other page. The exports stay for parity with the Next.js app.                                                                                                                                                                                                                                                                       |
| `prefetch()` / `navigation()` (`next/cache`)     | ❌     | Not exported by vinext's `next/cache` shim (`Missing export` at build). `@realworld/core`'s `vinext` export condition supplies no-ops, so gated content (cart, saved, reviews, recommendations) renders with the request and stays cached.                                                                                                                                                                                                                                                              |
| `instant` segment config                         | ❌     | `export const instant = true` is accepted and ignored (no validation, no warning).                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `instant()` from `@next/playwright`              | ❌     | vinext has no instant-navigation lock (the `next-instant-navigation-testing` cookie is never read). `e2e/cart.spec.ts` asserts that live stock and the per-session "Add to cart" button do appear inside an `instant()` scope; on Next.js they would be held back. The other `instant()` assertions (cached content visible) pass.                                                                                                                                                                      |
| View Transitions (`<ViewTransition>`)            | ⚠️     | Navigations call `document.startViewTransition` (1 call per product navigation, measured), and `<ViewTransition name share>` around resolved content (product card image → product page image) works. A `<ViewTransition>` around content that suspends, or inside a Suspense fallback (the shared `AnimatedSuspense`), breaks SSR: `Error: Element type is invalid: expected a string … but got: undefined`. The product page therefore uses plain `<Suspense>`.                                       |
| `<Suspense>` streaming with shared skeletons     | ✅     | Every per-session or uncached read streams into its own boundary with skeletons from `@realworld/ui` (live stock, cart badge, account menu, add-to-cart, save).                                                                                                                                                                                                                                                                                                                                         |
| `useOptimistic`                                  | ✅     | Add/remove from cart, save/unsave, and the cart quantity stepper update optimistically, then reconcile with the Server Function result.                                                                                                                                                                                                                                                                                                                                                                 |
| React Compiler                                   | ✅     | Enabled with `vinext({ react: { compiler: true } })` and `oxc-transform-react` (vinext does not use `reactCompiler` from `next.config`). The client chunks contain the compiler runtime's `memo_cache_sentinel`.                                                                                                                                                                                                                                                                                        |
| `generateStaticParams`                           | ⚠️     | Accepted; nothing is prerendered at build time (no `prerender` option is configured, and D1 is not reachable at build time).                                                                                                                                                                                                                                                                                                                                                                            |

Other observations:

- `"use cache"` KV keys embed the build machine's absolute source path (for example `…:["/Users/…/packages/core/src/product/product-queries.ts:$$hoist_4_getStockStatus",…]`), so keys differ between build machines and the path is visible in KV.
- `kvDataAdapter()`'s return type has `options?: … | undefined`, which vinext's `cache.data` descriptor type rejects under `exactOptionalPropertyTypes`; `vite.config.ts` spreads it with defined options.
- vinext's build route table classifies most routes as `?` (unknown): it cannot detect `cookies()` statically.
